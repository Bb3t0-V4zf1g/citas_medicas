1 · La idea en un dibujo

1 · LoginPOST /login con usuario y clave. La única vez que viaja la clave.
2 · TokenEl servidor revisa la clave contra el hash y responde un token firmado (30 min).
3 · Cada peticiónEl cliente manda Authorization: Bearer <token>.
4 · La API verificaRevisa la firma: ya sabe quién eres y tu rol, sin pedir la clave.

Después, cada petición pasa por cuatro preguntas, en orden. La API se detiene en el primer “no”:

PreguntaSi es “no”En el código
1. ¿Trae token?401usuario_actual()
2. ¿Es auténtico (firma) y vigente (exp)?401jwt.decode() / jwt.verify()
3. ¿Su rol puede hacer esto?403solo_encargado()
4. ¿El objeto es suyo?404WHERE id = ? AND usuario = ?
Autenticación = preguntas 1 y 2 (¿quién eres?). Autorización = preguntas 3 y 4 (¿qué puedes hacer?). Si pasa las cuatro, siguen las reglas de siempre: 422, 409, 201…

2 · Glosario

TérminoQué es, en una línea
TokenUn texto que el servidor te da al iniciar sesión y que presentas en cada petición, como un gafete.
JWTJSON Web Token: un formato de token con 3 partes en base64 separadas por puntos: cabecera, datos y firma.
FirmaLa tercera parte del JWT. Se calcula con los datos y una clave secreta del servidor. Si alguien cambia un solo carácter, deja de coincidir.
Firmado ≠ cifradoCualquiera puede leer los datos de un JWT; nadie puede cambiarlos sin la clave. Nunca metan contraseñas ni datos personales adentro.
sub, rol, expDatos del token: quién es, qué rol tiene y a partir de qué hora ya no se acepta.
Bearer“Portador”. El encabezado es Authorization: Bearer <token>: quien porta el token es tratado como su dueño.
HashUna huella de la contraseña que no se puede revertir. En el login no se “descifra”: se calcula el hash de lo que escribieron y se compara.
SalUn valor aleatorio que se mezcla con cada contraseña antes del hash: dos usuarios con la misma clave tienen hashes distintos.
bcryptUn algoritmo de hash lento a propósito (para frenar ataques de fuerza bruta). OWASP lo acepta con costo 10 o más; prefiere Argon2id.
RolQué tipo de usuario es (por ejemplo encargado o alumno). Decide qué operaciones puede hacer.
DueñoEl usuario al que pertenece un registro. Sale del token, nunca de lo que mande el cliente.
BOLA (API1:2023)Broken Object Level Authorization: ver o cambiar el objeto de otro cambiando su id en la petición. Es el incidente SEC-311.

Preguntas 1 y 2: verificar el token (401)

bearer = HTTPBearer(auto_error=False)      # lee "Authorization: Bearer ..."

def usuario_actual(cred = Depends(bearer)) -> dict:
    if cred is None:
        raise HTTPException(401, "Falta el token: inicia sesión en POST /login")
    try:
        datos = jwt.decode(cred.credentials, SECRETO, algorithms=["HS256"])  # firma y exp
    except jwt.InvalidTokenError:
        raise HTTPException(401, "El token no es válido o ya expiró")
    return {"usuario": datos["sub"], "rol": datos["rol"]}
function usuarioActual(req, res, next) {
  const [tipo, token] = (req.get('Authorization') || '').split(' ');
  if (tipo !== 'Bearer' || !token) return error(res, 401, 'Falta el token: inicia sesión en POST /login');
  try {
    const datos = jwt.verify(token, SECRETO, { algorithms: ['HS256'] });   // firma y exp
    req.yo = { usuario: datos.sub, rol: datos.rol };
    next();
  } catch (e) { return error(res, 401, 'El token no es válido o ya expiró'); }
}
function usuario_actual() {
  $h = $_SERVER['HTTP_AUTHORIZATION'] ?? (getallheaders()['Authorization'] ?? '');
  if (!preg_match('/^Bearer\s+(\S+)$/', $h, $m)) error(401, 'Falta el token: inicia sesión en POST /login');
  $d = verificar_jwt($m[1]);                 // revisa firma (hash_equals) y exp
  if (!is_array($d)) error(401, 'El token no es válido o ya expiró');
  return ['usuario' => $d['sub'], 'rol' => $d['rol']];
}
Indiquen siempre algorithms=["HS256"]: si no, algunas librerías aceptan el algoritmo que diga el propio token, y un atacante podría elegir uno sin firma.

Pregunta 4: el recurso con dueño (SEC-311, 404)

Decidan en equipo qué recurso de su proyecto tiene dueño (tareas, comentarios, citas, pedidos, viajes, inscripciones…). Dos reglas:

  1. Al crear, el dueño se toma del token, no del cuerpo.
  2. Al consultar, cambiar o borrar uno, el WHERE incluye al dueño. Si no hay fila: 404.
# crear: el dueño sale del token
con.execute("INSERT INTO prestamos (equipo_id, usuario, fecha) VALUES (?, ?, ?)",
            (datos.equipo_id, yo["usuario"], ahora))
# consultar uno: id Y dueño
fila = con.execute("SELECT * FROM prestamos WHERE id = ? AND usuario = ?",
                   (prestamo_id, yo["usuario"])).fetchone()
if fila is None:
    raise HTTPException(404, f"No existe el préstamo {prestamo_id}")
// crear: el dueño sale del token (req.yo)
db.prepare('INSERT INTO prestamos (equipo_id, usuario, fecha) VALUES (?, ?, ?)')
  .run(equipoId, req.yo.usuario, fecha);
// consultar uno: id Y dueño
const p = db.prepare('SELECT * FROM prestamos WHERE id = ? AND usuario = ?')
            .get(Number(req.params.id), req.yo.usuario);
if (!p) return error(res, 404, `No existe el préstamo ${req.params.id}`);
// con Prisma: findFirst({ where: { id, userId: req.yo.id } })
// crear: el dueño sale del token
$db->prepare('INSERT INTO prestamos (equipo_id, usuario, fecha) VALUES (?, ?, ?)')
   ->execute([$e['id'], $yo['usuario'], date('Y-m-d\TH:i:s')]);
// consultar uno: id Y dueño
$q = $db->prepare('SELECT * FROM prestamos WHERE id = ? AND usuario = ?');
$q->execute([(int)$id, $yo['usuario']]);
if (!$q->fetch()) error(404, "No existe el préstamo $id");
Si su tabla ya tiene un usuario_id y hoy lo leen del cuerpo, de la URL o de un parámetro, ese es su SEC-311. Cámbienlo por el del token.
¿Por qué 404 y no 403? Un 403 confirma que el registro existe. Con 404, nadie puede ir probando números para descubrir qué hay.

4 · Cómo probarlo a mano

Con curl, en cmd (Símbolo del sistema, no PowerShell)

curl.exe -i -X POST http://127.0.0.1:8000/login -H "Content-Type: application/json" -d "{\"usuario\":\"ana\",\"clave\":\"ana12345\"}"

:: copien el access_token (sin comillas) y guárdenlo en una variable de cmd
set TOKEN_ANA=eyJhbGciOi...

curl.exe -i http://127.0.0.1:8000/yo -H "Authorization: Bearer %TOKEN_ANA%"
curl.exe -i -X DELETE http://127.0.0.1:8000/equipos/1 -H "Authorization: Bearer %TOKEN_ANA%"

La última debe dar 403. Sin el -H "Authorization: …", 401.

Con /docs

  1. Ejecuten POST /login y copien el access_token.
  2. Botón Authorize (candado) → peguen el token → Authorize.
  3. Desde ahí, cada petición de /docs lleva el token.

Con las slides

Descompriman clase-s4.zip y corran python puente.py. Cada paso explica el comando, qué esperamos y por qué, y lo ejecuta en su computadora.

5 · Errores frecuentes

SíntomaCausa y solución
module 'jwt' has no attribute 'encode'Instalaron jwt en vez de pyjwt: pip uninstall jwt y pip install pyjwt.
401 en todo, aunque mandan el tokenFalta Bearer y un espacio, o el token lleva comillas.
“El token ya expiró”Pasaron los 30 minutos de exp. Vuelvan a hacer login.
Funciona en php -S pero no en ApacheApache puede quitar Authorization. Usen getallheaders() como en el ejemplo.
Prueba 16: “¡la respuesta incluye la clave!”El login regresa el usuario completo. Respondan solo el token.
Prueba 17 falla con 201El POST no pide token: falta Depends(...) o el middleware.
Prueba 19: “¡lo borró!”Piden token pero no revisan el rol (pregunta 3).
Prueba 20: “¡otro usuario lo pudo ver!”Falta el dueño en el WHERE (pregunta 4).
“No pude iniciar sesión como admin”Revisen "auth" en prueba.json: la ruta, los campos del login y campo_token.

6 · ¿Lo entendiste tú o lo entendió la IA?

Si usaron IA, al terminar tienen que poder contestar esto señalando su propio código. Son las preguntas del bloque 05 del artefacto y las que hace el revisor del PR.

  1. ¿En qué línea se crea el token y qué datos lleva?
  2. ¿En qué línea se verifica y qué responde si falta?
  3. ¿Dónde está la clave secreta y por qué no va en GitHub?
  4. En su consulta con dueño, ¿de dónde sale el usuario?
  5. ¿Qué pasa si quitan la línea del rol? ¿Y la del dueño?
  6. ¿Cómo está guardada la contraseña en su tabla?
Usen la IA como compañero que revisa, no como quien escribe. Pídanle “explícame línea por línea esta función”, “¿qué pasa si quito esta línea?”, “¿por qué aquí es 404 y no 403?”. Si piden “agrégale login a mi API” y pegan el resultado, pasan las pruebas pero no la revisión ni la entrevista.
